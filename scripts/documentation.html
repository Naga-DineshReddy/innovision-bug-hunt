1 Executive Summary & Competition Framework

1.1 Vision & Objectives

INNOVISION — BUG HUNT is a high-octane coding contest hosted by the Department of Artificial Intelligence and Data Science. Unlike conventional competitive programming contests where participants write code from scratch, BUG HUNT tests code comprehension, static analysis, logical error identification, and precision debugging under strict time constraints.

1.2 Multi-Round Competition Structure

The competition is structured into three progressive rounds totaling 100 marks. Every registered student begins in Round 1 and can qualify forward according to coordinator criteria:

Round Title & Focus Duration Questions Total Marks Default State
Round 1 Easy: Bug Hunt Basics
Syntax, arithmetic typos, conditional reversals, loop bounds		 10 Minutes 8 Questions 20 Marks LIVE
Round 2 Moderate: Debugging Challenge
Array indexing, dictionary lookups, off-by-one errors, recursion bases		 10 Minutes 5 Questions 30 Marks READY
Round 3 Hard: Final Bug Hunt
Algorithmic bugs, sorting, string manipulation, edge-case failure		 10 Minutes 3 Questions 50 Marks FINALISTS
TOTAL COMPETITION METRICS 30 Minutes 16 Questions 100 Marks —

1.3 Scoring Rules & Deterministic Tie-Breaker Algorithm

In high-stakes hackathons, ties often occur when contestants solve identical questions. The platform evaluates contestants and sorts the real-time leaderboard using an automated 4-tier tie-breaking algorithm:

Criterion 1
Total Score
Aggregate score across all rounds (Max 100). Primary rank order.
Criterion 2
Round 3 Score
Performance on hardest algorithmic challenges (Max 50).
Criterion 3
Round 2 Score
Performance on intermediate debugging challenges (Max 30).
Criterion 4
Earliest Submission
Contestant who submitted solutions earliest in UTC timestamp.

2 System Architecture & Technology Stack

2.1 High-Level Architecture Overview

The platform is built as a cloud-native, server-rendered and client-hydrated application leveraging Next.js 16 App Router, TypeScript, and Supabase PostgreSQL.

Architecture Pipeline
[ Participant Web Browser ]
      │
      ├── (1) HTTPS Student Session Cookie (HTTP-Only)
      ├── (2) Anti-Cheat Surveillance Signals (POST /api/student/anti-cheat)
      ├── (3) Monaco Code Editor (Browser WASM / WebWorker)
      │
[ Next.js 16 Application Server (Vercel / Node.js) ]
      │

      ├── Automated Test Case Evaluator (Input/Output assertion)
      ├── Session Management & JWT Token Generator

      └── Privileged Supabase Admin Client (SUPABASE_SERVICE_ROLE_KEY)

      ├── public.registrations & public.registration_members
      ├── public.participant_sessions (State & Live Scores)
      ├── public.submissions (Code snapshots & Test outputs)
      ├── public.competition_settings & public.rounds

      └── Row Level Security (RLS) Active Policies

2.2 Core Technology Stack Components

Frontend & UI Engine
  • Next.js 16.3.6 (App Router): High-performance server rendering and streaming.
  • React 19.2.8: Latest React concurrency features and state primitives.
  • Tailwind CSS 4: Zero-runtime styling with custom cyber dark-mode palette.

2.3 Dual-Engine Data Persistence (Hybrid Resilience)

To ensure zero event disruption during high-stress collegiate lab conditions (e.g., intermittent Wi-Fi or firewall blocks), the application employs a Hybrid Persistence Architecture (in src/lib/store.ts):

  • Primary Engine: Cloud Supabase database queried via supabaseAdmin with transaction integrity.
  • Fallback Engine: In-memory and static verified seed datasets (src/data/participants.ts, src/data/questions.ts). If Supabase credentials are unset or the network fails, the system seamlessly handles registrations and test scoring in memory without crashing.

3 Database Schema, Data Models & Row-Level Security

3.1 Relational Schema Architecture

The platform's relational model in Supabase PostgreSQL (defined in supabase/schema.sql) consists of 8 core tables:

Table Name Primary Key Foreign Keys / Indexes Description & Role
registrations id (UUID) registration_id (UNIQUE) Stores approved participant details synced with INNOVISION master database.
registration_members id (UUID) registration_id -> registrations Supports team members and full student profile metadata.
participant_sessions registration_id (VARCHAR) registration_id -> registrations Maintains live state, start/submit timestamps, scores (R1, R2, R3), finalist flag.
submissions id (UUID) registration_id, question_id Stores every code attempt, passed test counts, score, and execution duration.
competition_settings id (VARCHAR) Primary: main_settings Global configuration: tab limits, copy-paste flags, announcements, rules.
rounds round_number (INT) Values: 1, 2, 3 Round states (LOCKED, READY, LIVE, PAUSED, COMPLETED), durations, marks.
questions id (VARCHAR) round_id -> rounds Buggy code, hidden/visible test cases, explanations, marks, languages.
audit_logs id (UUID) registration_id, event_type Immutable anti-cheat trail (tab switches, paste attempts, blur events).

3.2 Row-Level Security (RLS) & Threat Mitigation

Threat Model & Vulnerability Resolution (rls_disabled_in_public)
Because client-side web applications expose NEXT_PUBLIC_SUPABASE_URL and NEXT_PUBLIC_SUPABASE_ANON_KEY, having tables with RLS disabled allows any tech-savvy participant to craft POST/DELETE requests using DevTools to overwrite competitor scores or delete questions.
Enforced Mitigation: RLS is strictly enabled across all tables. The public anonymous role is restricted to reading public settings and round statuses. All mutations, score writes, and participant updates are locked down exclusively to the server-side service_role key. 
-- Production Security Configuration
ALTER TABLE public.registrations ENABLE ROW LEVEL SECURITY;
ALTER TABLE public.registration_members ENABLE ROW LEVEL SECURITY;
ALTER TABLE public.participant_sessions ENABLE ROW LEVEL SECURITY;
ALTER TABLE public.submissions ENABLE ROW LEVEL SECURITY;
ALTER TABLE public.competition_settings ENABLE ROW LEVEL SECURITY;
ALTER TABLE public.rounds ENABLE ROW LEVEL SECURITY;
ALTER TABLE public.questions ENABLE ROW LEVEL SECURITY;
ALTER TABLE public.audit_logs ENABLE ROW LEVEL SECURITY;

-- Anonymous users can strictly read public contest metadata
CREATE POLICY "Public can view settings" ON public.competition_settings FOR SELECT USING (true);
CREATE POLICY "Public can view rounds" ON public.rounds FOR SELECT USING (true);

-- Backend API operations utilize the privileged service role (auth.role() = 'service_role')

4.2 Competition Arena Components

The competition arena (src/components/CompetitionArena.tsx) provides a responsive, IDE-like interface tailored for fast debugging:

Live Synchronized Countdown Timer
Calculated from server-stored round_deadline_at. Prevents client device clock manipulation. When timer hits zero, the arena disallows further keystrokes and automatically invokes the submission pipeline.
Question Navigator Matrix
Color-coded badge matrix allowing non-linear question navigation (when allowed by settings). Questions transition between UNATTEMPTED (slate), CURRENT (indigo ring), and SUBMITTED / CORRECT (emerald).
Monaco Code Editor Canvas
Full syntax highlighting, bracket matching, line numbers, and error diagnostics for Python. Contestants can revert accidental changes via "Reset to Starter Code" button.
Test Runner & Feedback Console
Dual test case strategy: Visible test cases showcase inputs and expected vs actual outputs. Hidden test cases evaluate edge boundaries to prevent hardcoded print statements.

4.3 Automated Evaluation & Submission Engine

When a student clicks "Submit Solution", the payload is transmitted to /api/student/submit:

  • The server evaluates the submitted code against all test cases associated with the question.
  • Score is calculated proportionally: (passed_cases / total_cases) * question.marks.
  • A permanent snapshot is recorded in submissions with timestamp and output logs.
  • The student's round total is dynamically recalculated and updated in participant_sessions.

5 Anti-Cheat Surveillance & Integrity Guard

5.1 Multi-Vector Integrity Protection

To preserve competitive fairness in computer lab environments, the application embeds an active anti-cheat sentinel (src/components/AntiCheatGuard.tsx) running client-side event loops:

Surveillance Vector Detection Mechanism Action Taken Logged Event Type
Tab / Window Switching document.visibilitychange & document.hidden Triggers visual compliance warning; increments violation tally. TAB_SWITCH
Focus Loss (Window Blur) window.addEventListener("blur") Detects split-screen or external messaging applications. BLUR
Clipboard Paste Attempt clipboard.addEventListener("paste") Intercepts paste event (e.preventDefault()); blocks external code insertion. PASTE_ATTEMPT
Fullscreen Exit document.fullscreenElement Alerts student to re-enter fullscreen mode immediately. FULLSCREEN_EXIT
Developer Tools Opening Window resize threshold analysis Prevents inspection of source code and client variables. DEVTOOLS

5.2 Violation Thresholds & Enforcement

Every detected violation fires an asynchronous beacon to /api/student/anti-cheat:

  • The violation is appended to the immutable audit_logs table with student registration ID, timestamp, and context details.
  • The participant's suspicious_count in participant_sessions is incremented.
  • If suspicious_count >= tab_switch_limit (configured in settings, default: 3), the server can flag the session for coordinator review or set status to DISQUALIFIED / LOCKED.
  • Coordinators can view real-time anti-cheat alerts directly on the live Admin Dashboard.
Coordinator Discretion & Manual Unlocking
Network fluctuations or accidental desktop notifications can occasionally cause focus blur. The platform therefore provides an Admin Unlock / Reset function in the coordinator panel to reinstate accidentally locked students.

6.2 Round State Machine Workflow

Coordinators transition rounds sequentially through the following state lifecycle: 

[ LOCKED ] ──────> [ READY ] ──────> [ LIVE ] <────> [ PAUSED ]
                                        │
                                        ▼
                                  [ COMPLETED ]
  • LOCKED: Students cannot access questions or view starter code.
  • READY: Round is queued. Contestants see a "Get Ready" countdown screen.
  • LIVE: Countdown clock ticks down. Editor is unlocked and active. Submissions accepted.
  • PAUSED: Coordinators freeze timers across all stations for announcements or lab issues.
  • COMPLETED: Round closes. All unsubmitted work auto-evaluates. Finalist selection unlocks.

7 Complete API Route & Endpoint Specification

All endpoints accept and return application/json. Authentication is validated via HTTP-only cookies or bearer headers.

7.1 Student API Endpoints

Method & Path Auth Request Payload Response Payload Function
POST /api/student/verify Public { registrationId: string } { success: boolean, participant: Participant } Validates ID, initiates session cookie, and returns student profile.
GET /api/student/round-session Student Cookie Query: ?round=1 { activeRound, deadline, questions, status } Returns active round parameters and questions (solution stripped).
POST /api/student/submit Student Cookie { questionId, code, roundId } { score, testsPassed, totalTests, results } Evaluates code, updates round scores, records submission snapshot.
POST /api/student/anti-cheat Student Cookie { eventType, details } { success, suspiciousCount, warning } Logs compliance events to audit_logs; increments violation count.
POST /api/student/complete-round Student Cookie { roundNumber: number } { success, nextRoundUnlocked, totalScore } Marks round as completed and handles transition to subsequent round.
POST /api/student/logout Student Cookie — { success: true } Clears student session cookies and ends active tracking.

7.2 Administrator API Endpoints

Method & Path Auth Payload / Parameters Description
POST /api/admin/login Public { email, password } Validates admin credentials, issues signed JWT session cookie.
GET /api/admin/dashboard/stats Admin Cookie — Returns total registered, active contestants, average scores, live audit feed.
GET/POST /api/admin/participants Admin Cookie Action: reset, unlock, disqualify Retrieves participant roster or updates participant operational status.
GET/POST /api/admin/rounds Admin Cookie { roundNumber, status, duration } Updates round state machine (e.g., transitions Round 1 to COMPLETED).
GET/POST /api/admin/finalists Admin Cookie { registrationIds: string[] } Promotes qualified students to finalist tier for Round 3 access.
GET /api/admin/submissions Admin Cookie Query: ?questionId=&round= Fetches raw submitted code and test outputs across contestants.
GET/POST /api/admin/settings Admin Cookie CompetitionSettings object Reads or updates global rules, tab limits, copy-paste permissions.

  • 3:40 PM: Competition finishes. Leaderboard exported for valedictory ceremony.

8.3 Disaster Recovery FAQ

Q: What if a lab PC crashes or the student accidentally closes their browser?
A: All submissions, scores, and active round deadlines are stored in Supabase PostgreSQL. The student simply re-opens the browser, types their registration ID at /login, and their exact session and scores will be restored instantly.
Q: What if a student is locked out due to accidental popups or antivirus notifications?
A: The coordinator can navigate to Admin > Participants, search for the student's Registration ID, and click "Unlock Session" or "Reset Strikes" to immediately re-enable their editor.
